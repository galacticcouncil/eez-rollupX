# Server development L2

Runs local L2 **424242** on the existing PoS L1 **414141** and
[PBS stack](PBS.md). The first profile enables
[Hydration rules](../../../docs/hydration/local-devnet.md) at genesis and uses
public test accounts. It uses the independent ECDSA proof signer; this is not a
ZisK deployment. Application settlement fees are disabled for initial bring-up;
the funded public poster pays L1 costs. Ordinary L2 gas fees remain enabled.

## Build local images

From the repository root, inspect the clean source revision and initialized
protocol pin first. These commands build the existing local Dockerfiles with
Rust 1.96.0, the locked dependencies and Foundry 1.7.1. Build node and signer
sequentially to limit memory use while the L1 continues producing blocks.
Choose fresh revision tags; never overwrite a tag used by this network.

```sh
revision=$(git rev-parse HEAD)
protocol=$(git ls-tree HEAD eez-core-protocol | awk '{print $3}')
tag=${revision:0:8}
sudo docker buildx build --builder default --platform linux/amd64 \
  --resource cpu-period=100000 --resource cpu-quota=800000 \
  --resource memory=32g --resource memory-swap=32g \
  --build-arg BUILD_PROFILE=release \
  --label org.opencontainers.image.revision="$revision" \
  --label io.eez.protocol.revision="$protocol" \
  --load -t "eez-devnet-node:$tag" .
sudo docker buildx build --builder default --platform linux/amd64 \
  --resource cpu-period=100000 --resource cpu-quota=800000 \
  --resource memory=32g --resource memory-swap=32g \
  --build-arg BUILD_PROFILE=release \
  --label org.opencontainers.image.revision="$revision" \
  --label io.eez.protocol.revision="$protocol" \
  --load -f Dockerfile.signer -t "eez-devnet-signer:$tag" .
sudo docker buildx build --builder default --platform linux/amd64 \
  --build-arg "EEZ_NODE_IMAGE=eez-devnet-node:$tag" \
  --build-arg FOUNDRY_VERSION=v1.7.1 \
  --label org.opencontainers.image.revision="$revision" \
  --label io.eez.protocol.revision="$protocol" \
  --load -f testing/kurtosis/Dockerfile.deploy -t "eez-devnet-deploy:$tag" .
sudo docker image inspect "eez-devnet-node:$tag" "eez-devnet-signer:$tag" \
  "eez-devnet-deploy:$tag" --format '{{.Id}} {{json .RepoTags}}'
```

These are local development images on this single Docker daemon. They do not
establish CI qualification or supply published release digests. Lark/Chiado
promotion must use the verified release artifact workflow and published images.
The one-shot deployment image uses the existing Kurtosis deployment Dockerfile;
the runtime topology is Swarm.

## Deploy once and start

Require healthy, finalized L1 and working PBS before broadcasting:

```sh
sudo bash scripts/local-devnet.sh check
sudo bash scripts/local-devnet.sh check-pbs
# Inspect the returned jobs and require successful task completion first.
sudo env "EEZ_DEVNET_DEPLOY_IMAGE=eez-devnet-deploy:$tag" \
  bash scripts/local-devnet.sh l2-deploy
sudo docker service ps eez-devnet-l2-deploy_deploy --no-trunc
sudo docker service logs eez-devnet-l2-deploy_deploy
# Require Complete with exit 0, then start:
sudo env "EEZ_DEVNET_NODE_IMAGE=eez-devnet-node:$tag" \
  "EEZ_DEVNET_SIGNER_IMAGE=eez-devnet-signer:$tag" \
  bash scripts/local-devnet.sh l2-start
sudo bash scripts/local-devnet.sh l2-status
```

The deployment task renders a chain-specific copy of `genesis.dev.json`, binds
a finalized L1 reference, deploys the unchanged pinned Core contracts, registers
rollup 1 and saves the genesis, network profile and addresses. The existing
deployment script checks genesis before its first broadcast. A persistent
`deployment-started` directory prevents automatic rebroadcast even after partial
failure; a completion marker and SHA-256 checks bind runtime startup to its
saved public configuration. Checksums detect accidental file changes. The
registered network profile/key binds the genesis block and settlement profile;
the complete L2 document digest binds Hydration role settings in RPC validation
identity. ECDSA still trusts the configured attester and does not attest its binary.

Storage is external and pinned to `platform.data=true`:

| Volume | Contents / writer |
| --- | --- |
| `eez-devnet-424242-deployment` | Public L1 genesis copy, generated L2 genesis/profile, addresses and markers; deployment task only |
| `eez-devnet-424242-broadcast` | Foundry receipts, including a partially completed deployment |
| `eez-devnet-424242-node` | Composer L2, embedded L1 and witness database |
| `eez-devnet-424242-beacon` | Dedicated Lighthouse follower of canonical L1 |

Node and signer mount the same deployment volume read-only. Copying only the
public L1 document there lets signer UID 65532 read it without mounting or
changing permissions on validator-generation directories. The embedded L1 is
driven by the dedicated beacon; it never shares canonical execution or builder
datadirs. The signer uses the public chain documents, with no L1 RPC access
configured. Its account is a public local-test fixture. The shared Engine JWT
is mounted only to the node and beacon, not the signer. The public fixture file
is intentionally not a source of real operator credentials.

## Interfaces and validation

No host ports are published. On `eez-devnet_l1`:

| Endpoint | Purpose |
| --- | --- |
| `http://eez-node:18688` | Standard L2 RPC, including ordinary transactions |
| `http://eez-node:18999` | L1 Composer cross-chain front |
| `http://eez-node:18998` | L2 Composer cross-chain front and EEZ request observations |
| `http://eez-beacon:5252` | Dedicated L1 beacon API |
| `eez-proof-signer:50061` | Internal prover gRPC |

Embedded L1 RPC is loopback-only inside the Composer task at `127.0.0.1:18545`.
Its authenticated Engine API is reachable by the dedicated beacon on port 18551.

Inspect service state and logs through Swarmpit or `sudo docker service ps` and
`sudo docker service logs eez-devnet-l2_eez-node` (likewise signer and beacon).
Allow embedded L1 synchronization and L2 timestamp catch-up before testing.
Use the Composer fronts for `eez_*` methods; standard L2 RPC does not serve them.

Run a state-changing semantic canary from an overlay task, once services are
ready. This spends public fixture gas and increments the counter:

```sh
stamp=$(date -u +%y%m%d%H%M%S)
sudo docker config create "eez-l2-canary-$stamp" deploy/swarm/devnet/l2-canary.sh
sudo docker config create "eez-l2-fixtures-$stamp" deploy/swarm/devnet/l2-fixtures.env
sudo docker service create --detach=true --name "eez-l2-canary-$stamp" \
  --restart-condition none --constraint node.labels.platform.data==true \
  --network eez-devnet_l1 \
  --mount type=volume,source=eez-devnet-424242-deployment,target=/out,readonly \
  --config "source=eez-l2-canary-$stamp,target=/canary.sh" \
  --config "source=eez-l2-fixtures-$stamp,target=/l2-fixtures.env" \
  --entrypoint bash "eez-devnet-deploy:$tag" /canary.sh
sudo docker service ps "eez-l2-canary-$stamp" --no-trunc
sudo docker service logs "eez-l2-canary-$stamp"
```

Require task exit 0 and `PASS`. The check requires chain identities, a successful
counter increment, and canonical L1 commitment advancement to a matching L2
block that includes the canary. Startup or a local receipt alone is insufficient.
This does not qualify cross-chain calls, independent follower replay, blob
reconstruction, restart recovery, fee refunds or production ZisK proofs.

The first live canary passed on 2026-11-26: counter 0 → 1 in L2 block 550;
the signer validated blocks 1–558; the one-blob batch landed in L1 block 13022.
The independent canary matched the canonical L2 block-558 hash
`0x5a73ab97d64f38723c240e53f3b7d75a663e20c9ecc3efe0597e0b3582727fa0`
to the registered rollup commitment. Local runtime images use revision tag
`5f8813d4` with the working Swarm configuration. This is canonical inclusion,
not an assertion that the settlement block had already finalized.

## Stop, recovery and upgrades

`sudo bash scripts/local-devnet.sh l2-stop` stops the three L2 services and
retains every volume. `l2-start` with the same image selections restarts them;
it does not deploy contracts or regenerate genesis. The L1/PBS lifecycle remains
separate: stop L2 consumers before stopping their L1. Do not delete data or
redeploy after a partial broadcast: inspect the saved receipts and reconcile
canonical transactions first. There is no automatic reset or deployment resume.

Back up all four L2 volumes with the L2 writers stopped, plus the paired L1/PBS
state and Engine JWT under their runbooks. Restore in isolation. No L2 restore
exercise has been completed. Composer accepted requests/retry counters are
in memory; database volumes do not guarantee durable queue recovery.

This is a fresh-genesis profile. Changing roles, counter seed or chain IDs
requires a separately named new network. Upgrades must preserve the authenticated
chain document and use compatible node/signer releases together; rollback to a
runtime without Hydration support stops the network. Incompatible validation
upgrades require the coordinated manager/key procedure in the
[deployment runbook](../../../docs/runbooks/chiado-deployment.md#rollup-manager-and-coordinated-upgrades).
